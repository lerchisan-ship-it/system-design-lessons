# Car Rental DB — результаты нагрузочного тестирования

Дата фиксации результатов: **29 сентября 2026**

## 1. Цель эксперимента

Цель — проверить, как PostgreSQL ведёт себя при росте объёма данных и на разных типах запросов:

- точечный поиск по индексируемому полю;
- последовательный просмотр больших таблиц;
- JOIN нескольких таблиц;
- агрегаты и группировки;
- сортировка;
- поиск по полю без подходящего индекса;
- сравнение планов выполнения через `EXPLAIN (ANALYZE, BUFFERS)`.

Тестирование выполнялось локально через DBeaver.

# 6. Результаты производительности

## 6.1. Поиск пользователя по email

План использовал `users_email_key`, `profiles_user_id_key` и `Nested Loop`.

| Запуск | Execution Time |
|---|---:|
| 1-й, холодный | 1,545 мс |
| 2-й | 0,038 мс |
| 3-й | 0,040 мс |

**Вывод:** после прогрева точечный поиск по уникальному email остаётся около **0,04 мс** даже на миллионе пользователей.

---

## 6.2. `COUNT(*)` по `users`

План: `Parallel Seq Scan` → `Partial Aggregate` → `Gather` → `Finalize Aggregate`, 2 worker-процесса.

| Запуск | Execution Time |
|---|---:|
| 1 | 135,074 мс |
| 2 | 124,189 мс |
| 3 | 128,934 мс |
| **Медиана** | **128,934 мс** |

Предыдущие этапы:

| Размер `users` | `COUNT(*)` |
|---:|---:|
| ~1 тыс. | 0,071 мс |
| ~10 тыс. | 0,465 мс |
| ~100 тыс. | 4,953 мс |
| ~1 млн | ~128,934 мс |

**Вывод:** точный подсчёт всей таблицы масштабируется значительно хуже точечного индексного поиска; на миллионе строк PostgreSQL уже использует параллельный последовательный просмотр.

---

## 6.3. История одного пользователя

Запрос проходил по цепочке `users → profiles → rentals` и использовал индексные сканирования.

**Execution Time:** **1,259 мс**

**Вывод:** небольшая история конкретного пользователя остаётся быстрой даже на 1,7 млн строк в `rentals`.

---

## 6.4. Поиск аренд с `rating_at_start = 15`

Отдельного индекса по `rating_at_start` нет.

План: `Parallel Seq Scan on rentals`.

**Execution Time:** **189,741 мс**

**Вывод:** чтобы найти около 150 строк по неиндексированному полю, PostgreSQL вынужден просмотреть практически всю таблицу `rentals`.

---

## 6.5. История одной машины + ДТП

Запрос: `cars → rentals → accidents`.

Использовались `idx_rentals_car`, `Bitmap Index Scan`, `Bitmap Heap Scan` и `accidents_rental_id_key`.

**Execution Time:** **5,257 мс**

**Вывод:** JOIN по трём таблицам остаётся быстрым, если выборка узкая и связи индексированы.

---

## 6.6. Топ аварийных машин

Задача: посчитать ДТП по всему нагрузочному автопарку, сгруппировать по машине и выбрать TOP-20.

План включал `Parallel Seq Scan`, `Parallel Hash`, `Parallel Hash Join`, агрегирование и сортировку.

**Execution Time:** **257,749 мс**

**Вывод:** массовый JOIN и агрегация по всему автопарку ожидаемо дороже точечного запроса, но на текущем объёме выполняется примерно за четверть секунды.

---

## 6.7. Выручка по маркам автомобилей

Задача: соединить `cars` и `rentals`, обработать примерно 1,7 млн аренд и сгруппировать по марке.

План: `Parallel Seq Scan` + `Parallel Hash Join` + агрегирование.

**Execution Time:** **308,050 мс**

**Вывод:** небольшое количество групп позволяет выполнить агрегацию значительно быстрее, чем группировку почти по миллиону профилей.

---

## 6.8. Топ клиентов по количеству аренд и сумме затрат

Задача: обработать 1 700 992 аренды, сгруппировать почти по миллиону `profile_id`, посчитать `COUNT(*)` и `SUM(total_cost)`, выбрать TOP-20.

План: `Index Scan` → `GroupAggregate` → `top-N heapsort`.

| Запуск | Execution Time |
|---|---:|
| 1 | 4 183,264 мс |
| 2 | 4 203,307 мс |

**Диапазон:** примерно **4,18–4,20 с**.

`top-N heapsort` использовал около 27 kB памяти; признаков ухода сортировки во временные файлы не наблюдалось.

**Вывод:** это самый тяжёлый из протестированных запросов. Основная стоимость связана с группировкой 1,7 млн строк по огромному числу профилей.

---

## 6.9. Фильтрация аренд по `started_at`

Имеющийся индекс `(profile_id, started_at)` не подходит для эффективного поиска только по `started_at`, потому что первым столбцом является `profile_id`.

План: `Parallel Seq Scan` → `Partial Aggregate` → `Gather` → `Finalize Aggregate`.

| Запуск | Execution Time |
|---|---:|
| 1 | 135,343 мс |
| 2 | 140,675 мс |
| 3 | 147,393 мс |
| **Медиана** | **140,675 мс** |

**Вывод:** наличие поля внутри составного индекса не означает, что индекс будет полезен для любого запроса по этому полю; порядок полей важен.

---

## 6.10. TOP-20 самых дорогих аренд

Отдельного индекса по `total_cost` нет.

План: `Parallel Seq Scan` → `top-N heapsort` → `Gather Merge` → `Limit`.

| Запуск | Execution Time |
|---|---:|
| 1 | 200,820 мс |
| 2 | 206,746 мс |
| 3 | 168,520 мс |
| **Медиана** | **200,820 мс** |

Сортировка использовала около 27 kB памяти на worker и не уходила на диск.

**Вывод:** PostgreSQL просматривает всю таблицу, но благодаря `LIMIT 20` использует top-N сортировку вместо полной сортировки всех 1,7 млн строк.

# 8. Основные выводы

1. **Размер таблицы сам по себе не делает запрос медленным.** Точечный поиск по индексируемому email остаётся около сотых долей миллисекунды даже на миллионе пользователей.
2. **Индекс полезен тогда, когда соответствует реальному шаблону запроса.** Поиск по `rating_at_start` без отдельного индекса требует полного просмотра `rentals`.
3. **Порядок полей в составном индексе важен.** Индекс `(profile_id, started_at)` полезен для истории конкретного профиля, но не для поиска только по `started_at`.
4. **`Seq Scan` не является автоматически плохим планом.** Если запросу нужна большая часть таблицы, последовательный просмотр может быть дешевле множества индексных обращений.
5. **PostgreSQL начинает применять параллелизм на больших объёмах.** В тяжёлых запросах появились `Parallel Seq Scan`, `Parallel Hash`, `Gather`, `Finalize Aggregate` и worker-процессы.
6. **JOIN больших таблиц может быть быстрым при узкой выборке и хороших индексах.** История одной машины с ДТП выполнялась примерно за 5 мс.
7. **Количество групп сильно влияет на стоимость агрегации.** Выручка по нескольким маркам заняла около 0,3 с, а группировка почти по миллиону профилей — более 4 с.
8. **`LIMIT` позволяет оптимизировать сортировку.** Для TOP-20 по `total_cost` PostgreSQL применил `top-N heapsort`.
9. **На текущем наборе данных признаков аварийной деградации БД не выявлено.** Самый тяжёлый запрос выполнялся около 4,2 секунды и представлял собой глобальную агрегацию по 1,7 млн строк и почти миллиону групп.

---

## 9. Возможные дальнейшие эксперименты

Можно отдельно проверить влияние новых индексов:

- по `started_at`;
- по `rating_at_start`;
- по `total_cost DESC`;

а затем повторить те же запросы и сравнить планы до/после. Для тяжёлого отчёта по клиентам можно дополнительно рассмотреть materialized view или отдельную агрегатную таблицу.

Важно: новые индексы стоит добавлять только при наличии реального сценария использования, потому что они занимают место и увеличивают стоимость операций записи.
