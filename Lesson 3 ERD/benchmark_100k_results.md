# Benchmark PostgreSQL — контрольная точка на 100 000 пользователей

Дата фиксации: **1 октября 2026**

## 1. Размер тестового набора данных

| Таблица | Количество строк |
|---|---:|
| `users` | 100 000 |
| `profiles` | 100 000 |
| `cars` | 10 000 |
| `rentals` | 170 000 |
| `accidents` | 11 000 |

Для каждого benchmark-запроса использовался:

```sql
EXPLAIN (ANALYZE, BUFFERS)
```

Базовые тесты запускались по **3 раза**. В итоговой таблице используется **медиана `Execution Time`**.

После массового засева была отдельно обновлена статистика планировщика:

```sql
ANALYZE users;
ANALYZE profiles;
ANALYZE cars;
ANALYZE rentals;
ANALYZE accidents;
```

Для тестов №7–10 после `ANALYZE` были выполнены повторные контрольные замеры.

## Тест 1. Поиск пользователя по email

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    u.user_id,
    u.email,
    p.full_name,
    p.driver_license
FROM users AS u
JOIN profiles AS p
    ON p.user_id = u.user_id
WHERE u.email = 'loadtest_user_0999@example.invalid';
```

| Запуск | Execution Time |
|---:|---:|
| 1 | 0,062 мс |
| 2 | 0,046 мс |
| 3 | 0,036 мс |
| **Медиана** | **0,046 мс** |

**Наблюдение:** точечный индексный поиск практически не изменился при росте базы.

## Тест 7. Выручка по маркам автомобилей

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    c.brand,
    COUNT(r.rental_id) AS rentals_count,
    ROUND(SUM(r.total_cost), 2) AS total_revenue,
    ROUND(AVG(r.total_cost), 2) AS avg_rental_cost
FROM cars AS c
JOIN rentals AS r
    ON r.car_id = c.car_id
GROUP BY c.brand
ORDER BY total_revenue DESC;
```

### Первичный замер

| Запуск | Execution Time |
|---:|---:|
| 1 | 111,852 мс |
| 2 | 107,192 мс |
| 3 | 107,313 мс |
| **Медиана** | **107,313 мс** |

### После `ANALYZE`

| Запуск | Execution Time |
|---:|---:|
| 1 | 94,819 мс |
| 2 | 102,822 мс |
| 3 | 100,967 мс |
| **Медиана** | **100,967 мс** |

План после `ANALYZE` включал:

- `Parallel Seq Scan on rentals`;
- `Hash Join` с `cars`;
- `Partial HashAggregate`;
- `Gather Merge`;
- `Finalize GroupAggregate`.

Признаков сброса промежуточных данных на диск не наблюдалось.

Дополнительный контрольный запуск с отключённым параллелизмом:

```text
Execution Time: 104,389 мс
```

**Наблюдение:** для этого запроса отключение параллелизма почти не изменило результат. Основная стоимость связана с массовым JOIN и агрегацией, а не с overhead `Gather`.

## Тест 8. Топ клиентов по количеству аренд и затратам

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT
    r.profile_id,
    COUNT(*) AS rentals_count,
    SUM(r.total_cost) AS total_spent
FROM rentals AS r
GROUP BY r.profile_id
ORDER BY
    rentals_count DESC,
    total_spent DESC
LIMIT 20;
```

### Первичный замер

| Запуск | Execution Time |
|---:|---:|
| 1 | 129,846 мс |
| 2 | 142,486 мс |
| 3 | 134,120 мс |
| **Медиана** | **134,120 мс** |

### После `ANALYZE`

| Запуск | Execution Time |
|---:|---:|
| 1 | 112,642 мс |
| 2 | 116,475 мс |
| 3 | 111,978 мс |
| **Медиана** | **112,642 мс** |

После роста данных PostgreSQL изменил стратегию агрегации:

```text
Index Scan using uq_rental_profile_start_date
        ↓
GroupAggregate
        ↓
top-N heapsort
        ↓
LIMIT 20
```

На маленьком объёме ранее использовался `HashAggregate`, а на 100 000 профилей планировщик воспользовался тем, что существующий индекс выдаёт строки в порядке `profile_id`, и перешёл на потоковый `GroupAggregate`.

Признаков нехватки `work_mem` и записи временных данных на диск не выявлено.

## Тест 9. Фильтр по `started_at` без отдельного ведущего индекса

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT COUNT(*)
FROM rentals
WHERE started_at >= TIMESTAMPTZ '2025-03-01 00:00:00+03'
  AND started_at <  TIMESTAMPTZ '2025-04-01 00:00:00+03';
```

### Первичный замер

| Запуск | Execution Time |
|---:|---:|
| 1 | 87,870 мс |
| 2 | 81,193 мс |
| 3 | 89,005 мс |
| **Медиана** | **87,870 мс** |

### После `ANALYZE`

| Запуск | Execution Time |
|---:|---:|
| 1 | 71,195 мс |
| 2 | 82,975 мс |
| 3 | 81,710 мс |
| **Медиана** | **81,710 мс** |

План:

```text
Parallel Seq Scan on rentals
        ↓
Partial Aggregate
        ↓
Gather
        ↓
Finalize Aggregate
```

### Эксперимент без параллелизма

Для текущей сессии:

```sql
SET max_parallel_workers_per_gather = 0;
```

Тот же запрос:

| Запуск | Execution Time |
|---:|---:|
| 1 | 7,176 мс |
| 2 | 6,793 мс |
| 3 | 6,529 мс |
| **Медиана** | **6,793 мс** |

План стал:

```text
Seq Scan on rentals
        ↓
Aggregate
```

Сравнение:

- параллельный план: **81,710 мс**;
- последовательный план: **6,793 мс**;
- последовательный вариант оказался примерно **в 12 раз быстрее**.

**Вывод:** на текущем локальном окружении overhead запуска и синхронизации parallel worker оказался существенно выше выигрыша от распределения работы.

# 5. Отдельные выводы по параллелизму

На масштабе 100k PostgreSQL начал активнее выбирать параллельные планы.

### Тест 7 — массовый JOIN + агрегация

- с параллелизмом: **100,967 мс**;
- один контрольный запуск без параллелизма: **104,389 мс**.

Разница минимальна: параллелизм почти не повлиял.

### Тест 9 — фильтр по периоду

- параллельный план: **81,710 мс**;
- последовательный план: **6,793 мс**.

Последовательный план оказался примерно **в 12 раз быстрее**.

### Тест 10 — TOP-20 по стоимости

- параллельный план: **97,568 мс**;
- последовательный план: **22,945 мс**.

Последовательный план оказался примерно **в 4,3 раза быстрее**.

### Общий вывод

Параллельное выполнение имеет собственную стоимость:

- запуск worker-процессов;
- распределение работы;
- синхронизация;
- обмен данными;
- `Gather` / `Gather Merge`;
- объединение частичных результатов.

Если полезная работа сама по себе невелика, overhead параллелизма может оказаться выше выигрыша.

Это не означает, что параллелизм следует отключать глобально. На более тяжёлых запросах или более крупных таблицах он может быть выгодным. Эффективность конкретного плана необходимо измерять на реальном объёме данных и в конкретной среде.

# 6. Краткий вывод по контрольной точке 100k

На 100 000 пользователей стали хорошо видны три разных типа масштабирования:

1. **Точечные индексные операции** почти не деградируют: поиск пользователя и история одного профиля остаются очень быстрыми.
2. **Полные просмотры, JOIN и агрегирование** растут заметно вместе с объёмом данных.
3. PostgreSQL начал менять стратегии выполнения — использовать параллельные планы и `GroupAggregate`. Некоторые решения оказались удачными, а некоторые дали существенный overhead на локальной машине.

Контрольная точка 100k показывает не только рост времени, но и то, как оптимизатор PostgreSQL адаптирует план при увеличении размера данных.
